# ADR-017: AI 에이전트는 모든 티켓을 추론 모델이 분류 · 계획하고 로컬 모델이 그 계획을 실행한다

- **상태**: 유효
- **날짜**: 2026-11-14
- **결정자**: 사용자 결정(2026-11-14), #208 · #213으로 구현
- **관련**: SRS `FR-075` · `FR-098` · `FR-101` · `FR-102`, [ADR-012](012-agent-acts-through-platform-gateway.md), [ADR-016](016-planner-model-nova-gateway.md), [AI 에이전트 설계](../design/AIagent.md) §9 · §10, [`ai-scope.md`](../ai-scope.md)
- **대체**: ADR-016의 로컬 모델과 나누는 방식

## 맥락

ADR-016까지는 이렇게 나눴다. 코드 정규식(①)이 case를 맞히면 거기서 분류가 끝났다. 못 맞히면 로컬 Qwen3-8B가 case를 골랐다. case가 정해지면 로컬 모델이 playbook의 계획과 도구 호출을 모두 했다(③). 추론 모델 `gpt-6.1-sol`은 playbook이 `gave_up`했을 때(④)와 case가 없을 때(⑤)만 불렸다.

2026-11-14 실서비스(app.stairnoworks.com)에서 실패를 심은 레포 `suda5936/WOOWANGTHON_TEST_2`로 9건을 한 번씩 돌렸다(`wcp-ai:5c7e72a`). 9건 중 5건은 playbook에 없는 실패였다(빌드 인자 누락, TypeScript 타입 오류, Dockerfile 오타, 없는 npm 패키지, `USER` 순서).

- 정답은 0/9였다. 9건 중 8건이 `TOOL_LIMIT`로 끝나 ④도 쓰이지 않았다.
- 로컬 모델은 playbook에 없는 5건을 모두 엉뚱한 case(B1 · B2 · B4)로 골랐다. 그래서 추론 모델은 9건 중 1건에서만 불렸다.
- 9건 중 7건은 도구를 부르기 전에 계획이 틀렸다(잘못 고른 case, 이 레포에 맞지 않는 playbook). 로컬 모델은 거절된 호출을 되풀이했다.

## 결정

1. **분류는 추론 모델이 한다.** 코드 정규식이 고른 후보는 힌트로만 준다. 추론 모델은 case를 하나 고르거나, 맞는 것이 없으면 없다(null)고 답한다. 로컬 모델의 분류는 없앤다.
2. **계획은 모든 티켓에서 추론 모델이 한다.**
   - 알려진 case: 추론 모델이 읽기 도구(`read_repo` · `get_target_status` · `read_pod_logs`)로 증거와 파일을 읽는다. playbook은 참고로만 보고 단계 계획(원인 한 줄, 단계마다 도구 · 실제 인자 · 조건)을 낸다. 바꾸는 도구는 이 단계에서 부르지 않는다.
   - 모르는 실패: 지금처럼 추론 모델이 도구를 직접 불러 끝까지 푼다(⑤).
3. **실행은 로컬 모델이 한다.** 로컬 모델은 계획에 있는 도구만 받는다. 그 도구를 계획대로 부르고, 학생에게 보일 해결 결과를 쓴다.
4. **실행 중 게이트웨이 거절을 받거나 로컬 모델이 `gave_up`을 내면, 로컬 모델이 혼자 다시 시도하지 않는다.** 그 자리에서 멈춘다. 그러면 추론 모델이 지금까지의 호출을 보고 다시 계획하고, 도구를 직접 불러 끝낸다(④, 티켓당 한 번).
5. **추론 API를 못 쓰면** 분류 · 계획 · 실행을 모두 로컬 모델이 한다(ADR-016과 같다).

## 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| ADR-016 그대로 두고 로컬 모델의 분류 프롬프트만 다듬기 | 바꿀 것이 적다 | 8B 모델이 목록을 받으면 없다고 하지 않고 하나를 고르는 경향을 프롬프트로 막을 근거가 없다. 코드로 맞힌 case에서도 playbook이 레포에 맞지 않아 틀렸다(B4 · B5w) |
| 계획과 실행 모두 추론 모델 | 실행 중 판단도 강한 모델이 한다 | 로컬 모델을 둔 이유(호출 대부분을 비용 없이 클러스터 안에서 처리, 데이터가 밖으로 덜 나감)가 없어진다. 실행 실수는 코드 가드(거절 시 재계획, 지어낸 env 값 막기)로 막는다 |
| 추론 모델이 도구 없이 계획만 하기(#208 처음 모양) | 추론 API 요청이 짧고 외부로 가는 데이터가 적다 | 파일 내용을 모른 채 계획해, 파일 전체 내용이 필요한 `edit_repo_file` 단계를 쓰지 못했다(실측 B4: "읽고 `needs_user`"로 계획). 그래서 계획 단계에 읽기 도구만 열었다(#213) |
| Qwen이 먼저 읽고 추론 모델이 한 번 더 계획 | 추론 모델은 도구를 부르지 않는다 | 추론 API 호출이 한 번 더 늘고, 무엇을 읽을지를 다시 로컬 모델이 정하게 된다 |

## 결과

- 쉬워지는 것: 정규식에 없는 실패도 추론 모델이 원인을 찾는다. 로컬 모델의 일이 "받은 단계를 그대로 하기"로 좁아진다. 개선 뒤 같은 9건에서 정답이 0/9에서 3/9가 됐다(`wcp-ai:a928cd0`, 한 번씩). 9건 모두 추론 모델이 계획했고 `TOOL_LIMIT`는 없었다.
- 어려워지는 것:
  - 모든 티켓의 요약 · 로그 조각과, 계획 단계에서 읽은 레포 파일 · Pod 로그가 학교 게이트웨이(mindlogic)와 모델 업체로 나간다. 보내기 직전 가림 필터(FR-102)는 그대로 걸지만, 모양으로 가리는 필터라 놓치는 값이 있을 수 있다.
  - 티켓마다 추론 API를 1~3번 더 부른다. AI 처리 시간의 중앙값이 92.7초에서 249.0초로 늘었다.
- 아직 확인하지 않은 것: 결과 칸 맞추기(#211), `run_render` 안내(#212), 계획 단계 읽기(#213)를 넣은 뒤의 실측. 한 번씩 돌린 결과라 해결률의 범위와 인과는 미검증이다.
- 다시 볼 조건: 추론 API의 시간 · 비용이 데모에 부담이 될 때, 로컬 모델이 실측에서 계속 계획을 어길 때, 외부로 보내는 데이터를 줄여야 할 때.
