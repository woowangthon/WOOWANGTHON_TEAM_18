# ADR-002: 학생 프로젝트는 R2 또는 k3s 클러스터(학교 PC 우선, 클라우드 VM 예비)에서 실행한다

- **상태**: `제안됨` (제안자: @seren-wib)
- **날짜**: 2026-10-26
- **결정자**: TBD
- **관련**: [`001-stack.md`](001-stack.md), [`design.md`](../design.md) §1 (구성도·구성 요소·흐름), [`hackathon.md`](../hackathon.md)

## 맥락

서비스는 학교 실습실에서 놀고 있는 PC를 묶어 학생 프로젝트를 대신 실행한다. 실행 위치와 연결 방식을 정해야 하는 이유는 다섯 가지다.

- 학교 PC는 학교 방화벽 안에 있어 밖에서 바로 접속할 수 없다. 나가는 연결(443, 가능하면 UDP)은 열려 있다고 가정한다. 이 가정과 PC 관리자 권한·복원 프로그램 여부는 학교에 확인한다([`design.md`](../design.md) §7 12번).
- 학교 PC는 리눅스다. k3s는 Windows 노드를 지원하지 않으므로 이 전제가 깨지면 이 ADR을 다시 쓴다.
- 학교 PC는 수업 시간에만 켜져 있고, 수업 중에는 사람이 쓴다. 학교가 24시간 켜 두는 데 동의하더라도 정전, 업데이트 재부팅, 누가 끄는 것, 학교망 장애는 우리가 막을 수 없다. 그래서 학교 PC만으로는 아래 배포 URL 유지를 걸 수 없고, 학교 밖에 항상 켜진 자리(클라우드 VM)를 하나 둔다.
- 학생 코드는 신뢰할 수 없는 코드다. 실행할 때만이 아니라 빌드할 때도 그렇고, 한 PC에 여러 학생의 코드가 같이 돈다.
- 배포 URL은 제출 마감(11.15 18:00)부터 심사(11.21)까지 살아 있어야 한다. 그 사이 학교 PC가 꺼져 있어도 시연이 되어야 한다.

## 결정

학생 프로젝트는 LLM이 분류한 실행 방식에 따라 R2 또는 k3s 클러스터에서 돌린다. 클러스터는 클라우드 VM 한 대(k3s 서버, 항상 켜짐)와 학교 실습실 PC(에이전트, 켜져 있을 때만)로 이루어지고, 둘은 Tailscale 사설망으로 잇는다.

| 단계 | 무엇을 | 어디서 |
| --- | --- | --- |
| 분석 | LLM이 정적 / 브라우저 실행 / 서버 필요로 분류하고 위험 코드를 표시한다 | api → LLM API |
| 빌드 | 필요할 때만 rootless BuildKit Job이 맡는다 | VM의 k3s |
| 정적 | api가 파일을 그대로 R2에 올려 학생 결과물 도메인으로 공개한다 | R2 |
| 브라우저 실행 | 빌드 Job이 빌드 결과를 R2에 올린다 | R2 |
| 서버 필요 | 빌드 Job이 이미지를 GHCR에 올리고, k3s가 Deployment·Ingress로 띄운다 | 학교 PC 우선, 없으면 VM |
| 사용자 요청 | VM의 Traefik(k3s 내장 Ingress)이 받아 Tailscale 위로 Pod에 보낸다 | VM |
| 우리 api (FastAPI) | 같은 클러스터 안에서 돌린다 | VM 노드 고정 |

규칙 네 가지. 세부는 [`design.md`](../design.md) §1.3.

- **배치**: 학생 Pod는 `required nodeAffinity`로 학교 PC에만. VM은 taint. Ready인 학교 PC가 하나도 없을 때만 api가 affinity를 바꿔 VM에 두고, 돌아오면 되돌린다.
- **이미지**: GHCR private. 노드는 읽기 토큰, 빌드 Job만 쓰기 토큰 Secret. 무료 한도에 닿으면 학생 이미지를 public으로.
- **격리**: 학생 네임스페이스는 PSA `restricted` + NetworkPolicy. 빌드는 k3s Job 안 rootless BuildKit, 나가는 연결은 허용 목록 프록시만.
- **경계**: VM은 80/443만 공개. 나머지 포트는 Tailscale 인터페이스에서만.

구성도, 구성 요소별 역할, 흐름, 아직 정하지 않은 항목은 [`design.md`](../design.md) §1과 §7에 있다. 레포 구성과 작업 방식은 [`hackathon.md`](../hackathon.md)와 [`AGENTS.md`](../../AGENTS.md) §5, 기술 선택과 폴더 구조는 [ADR-001](001-stack.md)에서 다룬다.

## 대안

| 대안                                                     | 장점                                                 | 버린 이유                                                                                                                                                                                                             |
| -------------------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 모든 프로젝트를 클라우드 VM에서 실행                     | 구조가 단순하고 PC 켜짐 여부를 신경 쓰지 않아도 된다 | 학교 유휴 PC를 쓰는 것이 서비스의 핵심이다. 프로젝트 수만큼 VM 자원과 비용이 늘어난다                                                                                                                                 |
| 학교 PC에 공인 주소·포트포워딩으로 직접 접속            | VPN 없이 연결된다                                    | 학교 방화벽 안이라 밖에서 바로 접속할 수 없다                                                                                                                                                                         |
| PC마다 도커만 설치하고 직접 배치                         | 쿠버네티스를 배우고 운영할 필요가 없다               | 자리가 남은 PC 고르기, 켜짐 감지, PC가 꺼졌을 때 재배치를 직접 만들어야 한다                                                                                                                                          |
| 모든 프로젝트를 학교 PC에서 실행                         | 실행 경로가 하나다                                   | 서버가 필요 없는 프로젝트까지 PC 켜짐에 묶인다. 정적 파일은 R2에서 바로 보여주면 된다. 학교가 24시간 운영에 동의해도 정전·재부팅·학교망 장애를 우리가 통제하지 못하므로 심사 기간 URL 유지를 학교 PC에만 걸 수 없다 |
| 학교 PC가 없으면 미리보기만 (초안)                       | VM 자원을 학생 프로젝트에 쓰지 않는다                | 심사 기간에 학교 PC가 꺼져 있으면 시연이 안 된다. VM을 예비 노드로 두면 같은 배치 규칙으로 해결된다                                                                                                                   |
| 빌드 작업기를 VM 프로세스로 두고 `docker build` (초안) | 가장 단순하다                                        | 학생 Dockerfile의 `RUN`이 메인 VM에서 root Docker 데몬으로 실행된다. k3s Job + rootless BuildKit이면 자원 제한과 네트워크 제한을 Pod 규칙으로 같이 건다                                                             |
| Nginx를 VM에 직접 설치해 요청 분배 (초안)                | 익숙하다                                             | 학생 앱이 생길 때마다 upstream 설정을 손으로 갱신해야 한다. Traefik은 k3s에 내장돼 Ingress 리소스만 만들면 라우팅과 TLS가 따라온다                                                                                    |
| api를 VM에서 docker compose로 따로 운영                  | k8s 없이 익숙한 방식으로 돌린다                      | Traefik 뒤에 들어가지 못해 TLS와 도메인을 따로 관리해야 하고, 클러스터를 조작할 kubeconfig를 밖에서 관리해야 한다. 클러스터 안에서 ServiceAccount로 권한을 주는 쪽이 설정이 적다                                      |

## 결과

- **쉬워지는 것**: 서버가 필요 없는 프로젝트는 학교 PC 상태와 상관없이 항상 보인다. 학교 PC가 전부 꺼져도 VM에서 시연이 된다. 배치, 재배치, 라우팅, TLS를 전부 k3s 리소스(Deployment + Ingress)로 다루므로 api 코드가 단순하다. PC를 추가해도 설정이 거의 늘지 않는다.
- **어려워지는 것**: 팀이 k3s 리소스(Job, Deployment, Ingress, NetworkPolicy, affinity/taint)를 다뤄야 한다. 격리 값, PC 사용자 몫, 예비 노드 상한은 측정 뒤에 정해야 한다. 미정 항목은 [`design.md`](../design.md) §7.
- **다시 볼 조건**: 학교가 실습실 PC 사용을 허가하지 않거나 시연 환경에서 학교 PC를 쓸 수 없으면, 같은 클러스터에서 VM 노드만으로 운영한다. 구조는 그대로고 노드만 줄어든다. 학교 PC가 리눅스가 아니거나 재부팅마다 복원되는 PC라면 에이전트 노드 방식 자체를 다시 본다(WSL2·리눅스 VM 안의 k3s는 네트워크와 자원 계산이 달라진다).
