# ADR-007: 로그인은 이메일 · 비밀번호로 하고, 레포 소유 확인은 계정에 연동한 GitHub로 한다

- **상태**: 유효
- **날짜**: 2026-11-04
- **결정자**: 태진, 유성, 현식
- **관련**: [시스템 정의서](../system-definition.md) §4.1 · §4.3, [ADR-002](002-bot-account-for-fix-prs.md)
- **대체**: ADR-001의 인증(GitHub OAuth 로그인), ADR-002의 학생 로그인 · 소유 확인(로그인한 GitHub 계정과 대조)

## 맥락

ADR-001은 로그인을 Supabase의 GitHub OAuth로 정했다. 그런데 심사위원에게는 테스트 계정을 건네야 한다([`hackathon.md`](../hackathon.md) 제출물 3). GitHub 로그인이면 그 테스트 계정이 우리 팀원의 GitHub 계정이 되고, 계정을 넘기는 순간 2단계 인증 같은 절차에 막혀 심사가 번거로워진다.

한편 "제출한 레포의 주인이 이 사용자인가"는 계속 확인해야 한다([시스템 정의서](../system-definition.md) §4.1 2단계). ADR-002는 이것을 로그인한 GitHub 계정으로 대조했으므로, 로그인이 GitHub가 아니면 그 근거가 사라진다.

## 결정

- 로그인과 가입은 Supabase Auth의 **이메일 + 비밀번호**로 한다. FE가 Supabase에 직접 로그인하고, 플랫폼 서버는 Supabase가 발급한 토큰을 공개 키(JWKS)로 **검증만** 한다. 플랫폼 서버에 로그인 · 가입 API는 없다.
- 학생은 로그인한 뒤 프로필에서 **GitHub 계정을 한 번 연동**한다(Supabase 수동 연동). 연동은 읽기 scope만 요청한다. 레포 소유 확인은 연동한 GitHub 계정의 ID와 레포 소유자 ID를 비교하고, 연동하지 않은 계정은 제출할 수 없다.
- 관리자는 단일 계정이고, 사용자가 고칠 수 없는 서버 쪽 값(`app_metadata`)으로 지정한다. 관리자는 GitHub 연동 없이 모든 프로젝트를 본다.

## 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| GitHub OAuth 로그인 유지 (ADR-001) | 로그인 한 번으로 소유 확인까지 끝난다 | 심사용 테스트 계정이 팀원의 GitHub 계정이 되어, 계정 공유와 2단계 인증 문제가 생긴다 |
| 제출할 때마다 GitHub 1회성 로그인으로 확인 | 연동 상태를 저장하지 않는다 | 제출할 때마다 승인이 필요하고 리다이렉트로 폼 상태가 사라진다. 플랫폼 서버가 OAuth 흐름(state 검증, 코드 교환)을 직접 구현해야 한다 |
| 이메일 · 비밀번호를 플랫폼 서버에서 직접 구현 | 사용자명 로그인이 된다 | 비밀번호 저장 · 재설정 · 세션 갱신을 우리가 책임진다. 공개 레포라 보안 부담이 크다 |
| 소유 확인 없음 | 가장 단순하다 | 남의 레포를 우리 클러스터에 배포하고, 봇이 남의 레포에 PR을 올릴 수 있다 |

## 결과

- 쉬워지는 것: 심사용 테스트 계정(이메일 · 비밀번호)을 그대로 건넬 수 있다. 소유 확인은 유지된다. 플랫폼 서버에는 비밀키 없이 토큰 검증만 남는다.
- 어려워지는 것: 학생은 가입과 GitHub 연동을 두 단계로 한다. 연동한 GitHub ID는 토큰에 들어 있지 않아, 플랫폼 서버가 Supabase 관리자 API로 조회해야 하고 그 키(service role)를 서버에 둔다. 수동 연동은 Supabase에서 아직 beta다. 학생이 연동을 해제할 수 있으므로 소유 확인은 제출할 때마다 한다.
- 다시 볼 조건: Supabase 수동 연동의 동작이나 지원이 바뀔 때, 사용자명 로그인이 필요해질 때.
