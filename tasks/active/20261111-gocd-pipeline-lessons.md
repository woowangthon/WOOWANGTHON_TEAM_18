- 2026-11-11: wrote the files, then ran them against a real GoCD 26.1.0 server in docker. Real-server findings that the docs and my first draft got wrong: (1) while login is off GoCD answers 401 to a request that carries credentials, so `setup.sh` sends them only after login is on; (2) a config repo needs a `rules` entry that lets its pipelines into their group; (3) an environment in the server's config cannot reference a config-repo pipeline (422), so a GoCD secure variable cannot hold the notify token; it is the agents' environment now; (4) a pipeline material with the same URL and branch as the config repo must have the same `auto_update`, so `auto_update: false` was refused, and manual approval of the first stage is what keeps commits from starting a run; (5) the access token API is `/go/api/current_user/access_tokens`; (6) `corepack enable` fails in the copied node folder because the yarn link points outside it (`corepack enable pnpm`); (7) `PLATFORM_API_URL` accepts http only on loopback, so `host.docker.internal` does not work for a local platform server: run it with `network_mode: service:aws-agent`.

- 2026-11-12: CodeRabbit review on #141, two findings taken (the third, Verify/Switch missing, is #152). Now `setup.sh` makes a second user `be`, names `admin` the only system administrator (system_admins API v2; with none named every user is one), creates the group `wcp` with `be` as view + operate only, and mints the token as `be`. ## Lessons

- GoCD's API docs and a real server disagree often enough (credentials refused while login is off, config repo `rules`, `auto_update` must match, token API path, `admins` vs `admin`) that every API call in `setup.sh` was settled only by a run against a real 26.1.0. Run a script like this against the real server image before review, not after.
- Least privilege for the platform server's GoCD token needs a second user: with no system administrator named, every user is one, and an admin token can register a config repo that runs commands on an executor holding the AWS key.
- curl 8.5 with `--retry` fails (exit 23) when it reads a header from `-H @-` or writes to `-o /dev/null`; use `-K -` for the header and a temp file for the answer.
- An idempotent setup script must compare what is already there, not only check that it exists: a rerun with other settings, or a state file outlived by the server's data, otherwise passes silently.
- 2026-11-13 (first real deploy on the leader executor): `job.sh setup` failed with `pnpm: command not found` (exit 127) and the run ended with `STAGE_NO_REPORT`. The leader agent gets node and corepack from the tools volume (`Infra/executor/agent.yaml`) but never runs `corepack enable`, unlike the AWS agent image. `setup` now calls `corepack pnpm ...`. The original failure message is not stored by the platform server (`deploy_runs.failure` keeps code, stage and service only): read it in the GoCD console log of the stage. Fake-CLI tests passed because a dev machine has pnpm on PATH; only a real run on the executor shows what its image lacks.
