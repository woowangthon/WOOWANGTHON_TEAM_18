- 2026-11-11: wrote the files, then ran them against a real GoCD 26.1.0 server in docker. Real-server findings that the docs and my first draft got wrong: (1) while login is off GoCD answers 401 to a request that carries credentials, so `setup.sh` sends them only after login is on; (2) a config repo needs a `rules` entry that lets its pipelines into their group; (3) an environment in the server's config cannot reference a config-repo pipeline (422), so a GoCD secure variable cannot hold the notify token; it is the agents' environment now; (4) a pipeline material with the same URL and branch as the config repo must have the same `auto_update`, so `auto_update: false` was refused, and manual approval of the first stage is what keeps commits from starting a run; (5) the access token API is `/go/api/current_user/access_tokens`; (6) `corepack enable` fails in the copied node folder because the yarn link points outside it (`corepack enable pnpm`); (7) `PLATFORM_API_URL` accepts http only on loopback, so `host.docker.internal` does not work for a local platform server: run it with `network_mode: service:aws-agent`.
- 2026-11-11: L1 (local BE container sharing the AWS agent's network, real Supabase with a temporary user and one deploy row, real GitHub reads for `start`, fake AWS keys, stubbed Build only in the second round): `start` answered 202 and called the schedule API; the Build job ran setup, `fetch-input`, `build`, `notify`; with fake AWS keys Build failed as the platform failure `UnrecognizedClientException` and the BE run became `failed` at stage `build`; with Build stubbed to pass, `work/` reached the Prepare job on the leader-role agent, Prepare failed `K8S_UNREACHABLE` (no cluster), notify reached the BE (`failed` at `prepare`); a new commit started no run; no token or AWS key in the job logs (grepped for the values). The temporary user (which cascades the deploy row and run rows) was deleted, zero rows left.
- 2026-11-12: CodeRabbit review on #141, two findings taken (the third, Verify/Switch missing, is #152). (1) The platform server's access token was an administrator's: it could register a config repo and so run a command on the AWS executor and read the AWS key. Now `setup.sh` makes a second user `be`, names `admin` the only system administrator (system_admins API v2; with none named every user is one), creates the group `wcp` with `be` as view + operate only, and mints the token as `be`. Checked on a real GoCD 26.1.0: the `be` token schedules (202) and cancels a stage (200), and gets 403 on registering a config repo, creating or changing a pipeline and the system administrators; `admin` still works; a second `setup.sh` run is the same. (2) When `setup` or the artifact fetch failed there was no built `notify` CLI, so the run stayed `running` for `STALE_RUN_MS`. `job.sh notify` now sends the same STAGE_NO_REPORT with curl when the CLI is not there. Two curl 8.5 surprises: `-H @-` fails under `--retry` (exit 23) and so does `-o /dev/null` (it cannot truncate on a retry); the header goes in with `-K -` and the answer to a temp file. Checked with a local server answering 503 twice and on a real GoCD job whose `setup` fails; the token is not in the job log.
