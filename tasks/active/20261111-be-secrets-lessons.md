# BE: secrets (W3) — lessons

## Log

- 2026-11-11: Stacked on `feat/be-k8s-space` (PR #106). Contract written and committed first, then sent to the FE session (#83). FE asked for partial per-key sends; the write-only RBAC (no `get`, no `patch`) makes that impossible, so a send replaces the service's whole Secret. Decided with that reason in the contract.

- 2026-11-11: An e2e test with a malformed body that contains a secret showed that Nest turns V8's JSON error (`Unexpected token 'l', "<start of the body>" is not valid JSON`) into a `BadRequestException` whose message goes back in the response. `ApiExceptionFilter` now answers a fixed text for it.
- 2026-11-11: `deploy_secrets` is keyed by slug and service, not by deploy, so a later deploy of the same project with the same keys is `in` without sending again.
- 2026-11-11: `/simplify` applied: `taggedSha256` reused, `validateSecrets` early return, `SecretsService.statusOf(spec)` (owner-free read for #82), the parse-error rule now fail-closed (every `BadRequestException` without `code`), the store's merge header derived from `on_conflict`. Left as known limits: concurrent PUTs on the same slug+service can interleave (the last `in` digest may not match the cluster); the per-service digest is an unsalted sha256 (an HMAC with a server pepper or a random generation id would remove the offline-guess risk, but `deploy-handoff.md` says "sha256 of the values", so ask the W4/W5 owner); `k8s` imports three regexes from `deploys/deploy-input` (leaf file, no cycle yet).
- 2026-11-11: The cluster-call module is owned by seren-wib (#111) and overlaps the k8s Secret code of the first version. Split: this branch is the HTTP API + DB + validation and calls the write through `SecretWriter`; the first version stays on the fork branch `feat/be-secrets` as a reference. `ensureSpace` is now the writer's job (one call per service write).
- 2026-11-11: #82 `/simplify` applied: spec helper `failure`, non-circular hash assertion, `DeployReadinessService` not exported (same module as the runs service). Left: the `deploys` row is read twice (here and in `DeployConditionService.prepare`), and the `secrets.<service>.<KEY>` path is built in two files. `DeployReadinessService` extends `DeployPreparer` and the module binds it with `useExisting`; the start e2e runs against that real binding.

## Lessons

- A "no values anywhere" claim needs a test that looks at every place at once (response, logs, database rows, requests to the database), with several malformed inputs. The first malformed-body test passed because its input did not trigger the leaking message.
- Record the state in the safe direction first (`writing`) and promote it after the external write; then a crash or a failure never leaves a state that claims more than is true.
- Worth promoting: the body-parse message pitfall is added to `BE/CLAUDE.md` Pitfalls.
- 2026-11-11: CodeRabbit on #119: an unkeyed sha256 of short secret values can be brute-forced from the DB row and from `secretHash` (pod annotation `wanggane/secret-hash`). Digests are now HMAC-SHA256 under a required server-only `SECRET_HASH_KEY` (>= 32 chars, boot fails without it); SSM must have `/wcp/be/SECRET_HASH_KEY` before the next BE deploy. Changing the key changes the stored digests' meaning, so `secretHash` changes until the values are sent again. The service digest and the combined hash carry a purpose prefix so they cannot collide.
